# 阶段 2：安全地基

本文件记录阶段 2 的管理员认证、Access Key 认证和资源凭证加密基础。后续管理 API、Gateway、Usage 和 Admin Web 已实现；管理员初始化现已改为 [网页首次设置](首次管理员初始化.md)。

## 已实现接口

| 方法与路径 | 认证 | 行为 |
| --- | --- | --- |
| `GET /api/v1/auth/setup` | 无 | 只返回是否需要初始化管理员 |
| `POST /api/v1/auth/setup` | 仅未初始化时 | 创建首位管理员；完成后返回 409，禁止重复初始化 |
| `POST /api/v1/auth/login` | 用户名和密码 | 返回 `data.token / tokenType / expiresAt` |
| `GET /api/v1/me` | Admin JWT | 当前有效管理员身份，BIGINT ID 返回字符串 |
| `POST /api/v1/auth/logout` | Admin JWT | 返回 `clearToken: true`，客户端清理 JWT |
| `POST /api/v1/members/{id}/keys` | Admin JWT | 创建 MEMBER 的 Access Key，完整值仅此次返回 |
| `POST /api/v1/access-keys/{id}/revoke` | Admin JWT | 幂等撤销 Key，并记录首次撤销 |
| `/anthropic/*` | Access Key | 认证失败返回原生格式 401；阶段 4 已接入 Messages 和 count_tokens 转发 |

管理员使用 `Authorization: Bearer <JWT>`。Gateway 使用 `x-api-key: <Access Key>` 或 `Authorization: Bearer <Access Key>`，同时携带两个认证 Header 会被拒绝。两种凭证不能互换；Gateway 不套用管理面的响应包装。

登录请求为 `{"username":"<设置的账号>","password":"<设置的密码>"}`；创建 Key 请求为 `{"name":"Claude Code","expiresAt":"2027-01-01T00:00:00Z"}`，有效期可省略。阶段 3 已提供成员创建接口，可先创建成员再签发 Key；自动化测试数据只在隔离 schema 创建。

## 管理员初始化和登录

- 新环境在网页创建首位管理员，账号为 1～64 bytes、密码为 12～72 bytes，没有默认账号密码，配置文件不保存管理员账号密码。
- 首次创建使用事务和 advisory lock，与初始化审计原子提交；存在任何管理员记录时不再创建，不覆盖密码或复活已删除账号。
- 密码使用 bcrypt，cost 为 12；数据库仅保存 Hash。未知用户执行 dummy bcrypt 校验。
- 连续失败默认 5 次锁定 15 分钟，可通过 `ADMIN_LOGIN_MAX_FAILURES / ADMIN_LOGIN_LOCK_DURATION` 调整。
- 同一账号登录尝试使用行锁，状态与操作日志在同一事务提交。认证失败也必须提交失败次数，不能随业务错误回滚。
- 锁定期间正确密码也被拒绝；到期后重新计数；成功清零失败次数、清空锁定并更新最后登录时间。
- 达到阈值的当次请求和锁定期间的重试返回 HTTP 429 / `ACCOUNT_LOCKED`，携带 `data.lockedUntil`、`data.retryAfterSeconds` 和 `Retry-After` 响应头。前端按账号显示倒计时并暂时禁用登录，到期后允许重试；刷新后由下一次登录请求重新确认锁定状态。未知账号及未达到阈值的密码错误仍返回 401 / `UNAUTHENTICATED`。
- JWT 固定 HS256、issuer 和 audience，包含管理员 / 组织 ID、签发与到期时间、随机 jti，有效期 8h。
- 每次管理请求检查数据库中的管理员和组织状态，停用或删除后已有 JWT 立即失效。
- 每次管理请求还检查管理员凭证版本；`zentrola password --username <账号>` 重置密码后旧 JWT 失效，同时解除临时锁定并记录审计，详见 [命令行与密码恢复](命令行与密码恢复.md)。
- 不提供 Refresh Token 或服务端 Session。退出由客户端清理 JWT；未到期且未失效的旧 JWT 仍可使用。

`ADMIN_JWT_SECRET` 必须是至少 32 随机 bytes 的 Base64，并与 Master Key 独立；共用同一密钥时启动失败。当前开发环境保留原管理员账号，已有密码不因升级而改变。

新环境可在 PowerShell 生成独立随机配置值，再填入 `.env`：

```powershell
$rng = [Security.Cryptography.RandomNumberGenerator]::Create()
$bytes = New-Object byte[] 32
$rng.GetBytes($bytes)
[Convert]::ToBase64String($bytes)
$rng.Dispose()
```

每个用途分别生成，不复用输出；管理员密码也可使用上述独立随机值。

## Master Key 和凭证加密

优先级为显式 `ACP_MASTER_KEY`、`ACP_MASTER_KEY_FILE` 外部文件、本地持久化文件、首次随机生成。配置加载遵守 System ENV > `.env` > 默认值。Key 必须是 32 bytes 的 Base64；非法显式配置或损坏的已有文件会阻止启动，不会静默覆盖。

本地默认路径 `data/secrets/master.key`，容器路径 `/data/secrets/master.key`。首次生成使用 `crypto/rand`，先写临时文件并同步，再原子发布且不覆盖已有文件；并发初始化读取获胜者写入的 Key。Unix 文件权限为 `0600`，Windows DACL 仅允许当前用户和 SYSTEM。外部 Secret 文件由部署方管理权限；Compose 使用外部文件时需自行添加只读挂载并设置路径。

AES-256-GCM 每次生成新 12-byte Nonce，存储密文、Nonce 和 `key_version=1`。AAD 绑定组织、Provider 和 Resource ID，阻止把密文挪到另一资源解密。不实现 Master Key Rotation 或 Envelope Encryption。

启动时检查 ACTIVE Resource 的可解密性；若本地 Key 丢失后新生成 Key，旧资源直接停用；其他无法解密的资源也停用，并写入 `RESOURCE_STATUS_CHANGE` 操作日志，原因为 `CREDENTIAL_UNRECOVERABLE`。保留现有状态枚举，管理员仍可登录以恢复配置；阶段 3 已提供重新录入 Credential 和切换资源状态的入口。

Master Key 不进入数据库、响应或日志。运行日志只记录安全诊断；操作日志的快照采用白名单，记录状态、失败次数、Key 前缀等信息，不保存密码、JWT、完整 Access Key 或 Credential。

## Access Key

新签发密钥使用 `vk-` 加 32 随机 bytes 的 URL-safe Base64（43 个字符），数据库只存完整密钥的 SHA-256 摘要及 `vk-` 后 8 个字符组成的识别前缀。成员列表的“密钥”列直接展示前缀加 `********`，完整值仍仅在创建时返回一次。已签发的 `zt_vk_` 密钥保持有效，按原文摘要认证、按原前缀脱敏展示；修改前缀不能转换已有密钥。创建和撤销校验组织归属与有效管理员，创建还要求有效 MEMBER。认证直接查询数据库中的撤销、过期、主体和组织状态，不使用缓存，因此状态变化立即生效。

完整 Key 只在创建成功的响应返回，相关响应使用 `Cache-Control: no-store`。创建与撤销操作日志和数据修改同事务提交。
