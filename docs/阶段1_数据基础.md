# 阶段 1：数据基础

本文件记录阶段 1 的核心数据模型与 Migration 交付范围；后续已完成的安全认证和管理 API 见 README 与对应阶段文档，真实 Claude Code 调用链路仍待 Gateway 阶段实现。

## 表结构

共 14 张业务表：

| 分类 | 表 |
| --- | --- |
| 组织与管理身份 | `organization`、`admin_user` |
| 调用主体与凭证 | `principal`、`access_key` |
| 分组与授权 | `ai_group`、`principal_group`、`group_model_permission` |
| 模型与资源 | `ai_provider`、`ai_model`、`provider_model`、`ai_resource` |
| 调用事实 | `ai_request`、`usage_record` |
| 管理操作日志 | `operation_log` |

SQL 定义位于 `internal/infrastructure/postgres/migrations/00002_core_schema.sql`，表和字段均附中文 COMMENT。

## 关键约束

- ID 为应用侧生成的正数 BIGINT，无业务自增序列。使用 Sonyflake，固定 epoch，不把数据库 ID 当作权限凭证。
- 可变表具备 `is_deleted / created_by / updated_by / created_at / updated_at`；事实和操作日志表不机械继承这些字段。
- 软删除业务唯一约束采用 Partial Unique Index；删除后重新创建分配新 ID，不复活原记录。
- 当前组织通过有效记录上的常量唯一索引限制为一个；未来多组织需要显式迁移，不开放创建流程。
- `principal_group` 从第一版即多对多，唯一约束为有效的 `(principal_id, group_id)`。
- `provider_model` 对有效 `(provider_id, model_id)` 唯一，每个逻辑模型至多有一个 ACTIVE 映射。
- `ai_resource` 只关联 `provider_id`，每个组织、Provider 至多一个 ACTIVE Resource，可以共同服务多个模型。
- 不创建 Foreign Key 或 Cascade Delete；未来管理写入由 Application 在事务内校验组织归属、关联对象存在性、状态与删除依赖。
- 操作日志有 Append Only 触发器，普通 UPDATE、DELETE、TRUNCATE 被拒绝。未来 Retention 必须引入专用维护流程；当前不实现日志清理任务。

## 字段语义

- `access_key` 额外明确 `organization_id`，与总方案的组织边界一致；`key_hash` 为 32-byte SHA-256 摘要，只有摘要与前缀字段，没有明文 Key 字段。
- Resource 的 `credential_ciphertext` 和 `credential_nonce` 使用 BYTEA，Nonce 为 12 bytes，密文含 GCM 认证标签，`key_version` 为正整数。阶段 1 只验证存储能无损承载标准 AES-GCM 数据，业务加密模块在阶段 2 实现。
- `locked_until / expires_at / revoked_at / last_used_at / last_active_at` 等“尚未发生或未配置”的值允许 NULL；不使用空字符串或虚假时间。
- Token 为 BIGINT，NULL 表示上游没有提供可信数据；0 表示已确认零用量。
- `cost_amount` 为 NUMERIC(20,8)，与 `cost_currency` 同时有值或同时为 NULL；MVP 未计算成本时保持 NULL。
- `billing_quantity` 使用 NUMERIC(20,8) 以容纳计量小数，Token 专用计数字段仍为 BIGINT；不使用 float，也不实现 Billing 或 Cost 计算。
- `ai_request` 记录已认证主体的最终请求事实；未知模型允许 `model_id=NULL`。未识别 Principal 的认证失败不伪造主体 ID。
- `usage_record` 仅用于真正发起的上游 Attempt，`attempt_no=1`，以 `(request_id, attempt_no)` 唯一；未调用上游时不虚构 Attempt。
- 事实状态为 `SUCCESS / FAILED / CANCELLED`，失败及取消需要稳定错误码。记录在请求结束时写入，因此 `completed_at` 必填。
- 时间使用 TIMESTAMPTZ，应用连接统一设置 UTC。

这些写入语义在阶段 4/5 接入 Gateway 和 Usage Writer 时落地，当前已建立相应字段和数据库约束。

## Bootstrap

正常启动在 Migration 后执行单个事务，创建默认组织、Anthropic Official、Sonnet / Opus 逻辑模型及两个上游映射，ID 全由应用侧生成。

并发启动由 PostgreSQL 事务级 advisory lock 串行化。任意插入失败回滚整个初始化事务。组织历史记录作为首次初始化标志，包含软删除记录；初始化过就不重新 Seed，不覆盖名称、状态、映射或恢复已删除对象。

阶段 1 交付时没有创建管理员或 Resource Credential，readiness 因 Master Key 未实现而返回 503。阶段 2 已接入显式初始密码创建管理员及 Master Key 持久化；依赖正常时 readiness 返回 200，详见 [阶段 2 安全地基](阶段2_安全地基.md)。

## 验证

`TestStage1Integration` 在随机隔离 schema 中检查中文 COMMENT、NOT NULL 例外、ID 类型与默认值、金额类型、无外键、Partial Unique Index、单组织和资源映射约束、Default Deny 与多组并集、AES-GCM 字节往返、Attempt 唯一性、操作日志只追加、Bootstrap 事务与重复启动保护。

测试结束执行该 schema 的 Down Migration 并删除空 schema；不在业务 schema 执行破坏性回滚。生产升级继续采用前向 Migration。
